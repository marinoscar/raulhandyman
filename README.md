# raulhandyman.net

Website for **Raul Handyman** — handyman and home repairs in Conroe, The Woodlands and nearby areas, Texas.

- **Stack:** Astro (static output) → nginx container → `proxy-nginx` on the marin VPS
- **Live URL:** https://raulhandyman.net (`www` redirects to the apex)
- **VPS location:** `/opt/infra/apps/raulhandyman` · container `raulhandyman-web` · `127.0.0.1:8330`

## Editing content

| Content | Where it is edited |
|---|---|
| Projects (description, photos, SEO text, publishing) | The admin app at https://admin.raulhandyman.net. See [Projects](#projects). |
| Business facts, towns, services, homepage FAQ | One file: [`src/data/site.ts`](src/data/site.ts) |

| To change | Edit in `src/data/site.ts` |
|---|---|
| Phone, email, Google profile links | `business` |
| Towns in the service area | `towns` |
| Services (adds/removes a page automatically) | `services` |
| Homepage FAQ | `homeFaq` |

`src/pages/index.astro` still reads loose photos from `src/assets/work/` (the older "Recent jobs" section). New job photos belong in a project in the admin, which gives them alt text, SEO text and their own page.

When `googleReviewUrl` is set, a "Leave a Google review" section appears. When `googleBusinessUrl` is set, it is added to the structured data as `sameAs`.

## Projects

A project is a description plus before/after photos. It becomes a page at `/projects/<slug>/`, an entry in the `/projects/` listing, a "Recent projects" strip on the home page and the matching service page, and a gallery. The pages are static: the site has no public API and no client JavaScript.

### How content flows

```
admin.raulhandyman.net   an editor adds a project, photos are processed, AI drafts the text,
        |                the editor reviews and presses Publish (this bumps the content version)
        v
GET /api/site/content            the published manifest (build token, permission site_content:read)
GET /api/site/content/version    the version string the cron compares
GET /api/site/media/<photoId>/<rendition>   the image files
        ^
VPS cron, every 2 minutes: deploy.sh --content
        |  version changed?  yes -> docker build (the build stage runs scripts/fetch-content.mjs)
        v
raulhandyman.net         static Astro + nginx, images self-hosted on the apex domain
```

- The manifest contract is [`src/content/manifest.schema.json`](src/content/manifest.schema.json) (required: `manifestVersion`, `contentVersion`, `generatedAt`, `projects`, `redirects`; optional `indexNowKey`). `scripts/fetch-content.mjs` validates against it and fails the build on a mismatch. The service and town ids come from [`src/data/catalog.json`](src/data/catalog.json), shared with the admin.
- `fetch-content.mjs` writes generated, git-ignored files: `src/content/projects/<slug>.json`, `src/assets/projects/<slug>/*.jpg`, `src/content/redirects.json` and `public/<indexNowKey>.txt`.
- A failed content build leaves the running site untouched and is reported to the admin (notification `site.build_failed`). A version that failed is retried at most every 30 minutes.
- Operating the pipeline (DNS, token, cron, rollback): [docs/runbook-admin.md](docs/runbook-admin.md). The admin app itself: [admin/README.md](admin/README.md).

### Local build: fixtures or the live API

| Mode | Command | Content |
|---|---|---|
| Fixtures (default) | `npm run dev`, `npm run build:prod` | Synthetic projects from `fixtures/content` (generated by `npm run fixtures`, no real photos). Used by CI. |
| Live API | `CONTENT_API_URL=http://127.0.0.1:8340 CONTENT_API_TOKEN_FILE=/path/to/token npm run build:prod` | The published projects of a running admin. Without a token the script falls back to fixtures. |
| Production (Docker) | set by the `Dockerfile` (`CONTENT_MODE=production`) | **Never fixtures.** No `CONTENT_API_URL`: an empty portfolio (`/projects/` is `noindex` and left out of the sitemap). A URL without a token: the build fails. |

`CONTENT_API_TOKEN` is also accepted in place of the token file. A token never appears in an image layer: Docker mounts it as a BuildKit secret.

### The CI gate

`.github/workflows/site-ci.yml` runs on every push and pull request that touches the site (not `admin/**`, not Markdown):

1. `npm run build:prod` with fixture content.
2. `npm run check` (`scripts/check-dist.mjs`): per-page HTML size (50 KB, 14 KB brotli), one `<h1>`, title 10-70 and description 70-160 characters, canonical, image `alt`/`width`/`height`, no JavaScript, valid JSON-LD, no broken internal links or anchors.
3. Lighthouse CI (`lighthouserc.cjs`, 3 runs, mobile emulation) on `/`, `/drywall-repair/`, `/projects/` and the first fixture project.

| Lighthouse assertion | Level |
|---|---|
| performance, seo, accessibility, best-practices score >= 0.98 | error (fails CI) |
| largest-contentful-paint <= 1800 ms | error |
| cumulative-layout-shift <= 0.02 | error |
| total-blocking-time <= 50 ms | warning only |

**Reading the report.** The run uploads the `lighthouse-reports` artifact (the `.lighthouseci` folder: one JSON and HTML report per run). Download it from the workflow run, open an `.html` file in a browser, and start at the failing category. To reproduce locally: `npm run build:prod && npx @lhci/cli@0.14.0 autorun --config=lighthouserc.cjs`.

> Not verified in the environment that wrote this document: the Lighthouse gate on a CI runner.

## SEO built in

- One page per service, each with a unique title, description, H1 and canonical URL
- JSON-LD: `HomeAndConstructionBusiness` + `WebSite` on the homepage, `Service` + `BreadcrumbList` on service pages
- `sitemap-index.xml` (auto-generated) and `robots.txt`
- Open Graph / Twitter card image (`public/og.jpg`)
- Self-hosted, preloaded fonts; responsive WebP images; static HTML with no client-side JS framework
- Trailing-slash URLs everywhere, `www` → apex 301, HTTP → HTTPS 301
- One page per project at `/projects/<slug>/` with its own title, description, canonical and structured data; the `/projects/` listing; a branded Open Graph image per project
- `image-sitemap.xml` (listed in `robots.txt` next to `sitemap-index.xml`); `/projects/` stays `noindex` and out of the sitemap while there are no projects
- Old project slugs redirect (301) through `dist/_redirects.map`, generated at build from the manifest's `redirects`
- IndexNow: after a build goes live the admin pings search engines with the changed URLs; the key file `/<key>.txt` is written into `public/` at build
- Build gates: `npm run check` and the Lighthouse thresholds above

After launch, validate with Google's [Rich Results Test](https://search.google.com/test/rich-results) and submit `https://raulhandyman.net/sitemap-index.xml` in Search Console.

## Deploy

Follows the `marin-server-infra` pattern: app folder under `/opt/infra/apps`, localhost-bound container, per-host config in `proxy/nginx/conf.d`, certbot webroot certificates.

```
deploy/
  compose.yml           → copied to /opt/infra/apps/raulhandyman/compose.yml
  raulhandyman.conf     → copied to /opt/infra/proxy/nginx/conf.d/raulhandyman.conf
  install.sh            first-time install (DNS check, build, certificate, proxy, verify)
  deploy.sh             update to latest main, with health check and rollback
```

### First install (once)

Prerequisite: DNS in GoDaddy points to the VPS — `A @ → <VPS IP>` and `CNAME www → raulhandyman.net`. Check with `dig +short raulhandyman.net`.

```bash
mkdir -p /opt/infra/apps/raulhandyman
cd /opt/infra/apps/raulhandyman
git clone https://github.com/marinoscar/raulhandyman.git repo
bash repo/deploy/install.sh
```

Then record it in the infra repo:

```bash
cd /opt/infra
git add apps/raulhandyman/compose.yml proxy/nginx/conf.d/raulhandyman.conf
nano SERVER.md          # add raulhandyman.net, port 8330
git commit -m "Add raulhandyman.net static site"
```

### Updates

Push to `main`, then on the VPS:

```bash
/opt/infra/apps/raulhandyman/deploy.sh           # deploys only if main has new commits
/opt/infra/apps/raulhandyman/deploy.sh --force   # rebuild anyway
/opt/infra/apps/raulhandyman/deploy.sh --content # rebuild only if the admin published new content (what the cron runs)
```

`install.sh` installs `/etc/cron.d/raulhandyman-content` (every 2 minutes, output in `/var/log/raulhandyman-content.log`) and a weekly logrotate. A site that has no admin yet has an empty `.content-token`, so `--content` exits silently and the site builds an empty portfolio. The admin app is **not** part of the site image (`.dockerignore` excludes `admin/`); it is deployed separately: see [docs/runbook-admin.md](docs/runbook-admin.md).

`deploy.sh` tags the running image as `raulhandyman-web:previous` before building. If the new container fails its health check, it restores that image and resets the repo to the previous commit.

### Useful commands

```bash
docker logs --tail 50 raulhandyman-web
curl -s http://127.0.0.1:8330/healthz
curl -I https://raulhandyman.net
openssl x509 -enddate -noout -in /opt/infra/proxy/letsencrypt/live/raulhandyman.net/fullchain.pem
```

The content token lives at `/opt/infra/apps/raulhandyman/.content-token` (mode 600, never in git). The admin API is expected at `http://127.0.0.1:8340`; set `ADMIN_API_URL` to override.

Certificates renew through the existing `/opt/infra/shared/renew-all-certs.sh` cron job.
