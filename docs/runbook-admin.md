# Runbook: Deploy and operate the projects admin

> **Audience:** operators · **Code:** [`admin/`](../admin/README.md), [`deploy/`](../deploy/deploy.sh) · **Admin UI:** `https://admin.raulhandyman.net/admin/settings/...` · **Permission:** administrator (`INITIAL_ADMIN_EMAIL`)

Use this runbook to put the admin app on the VPS next to the static site, connect the two with a build token, and keep content rebuilds healthy. After it, an editor publishes a project in the admin and the site rebuilds within about 4 minutes (the cron runs every 2 minutes).

## Status of the steps

Nothing in this runbook was run when it was written: the author had no VPS, Docker host, Google client, storage bucket or OpenAI key. Every step is therefore labelled **to be verified on the VPS (issue #45)**. When you run a step and it behaves as described, change its label to **verified** with the date. Commands were checked against the scripts in this repository (`deploy/deploy.sh`, `deploy/install.sh`, `deploy/compose.yml`), not executed.

Not verified in the writing environment: the Docker and VPS deploy, real OpenAI calls, a real storage provider, the GreptimeDB metric table names, and the Lighthouse gate on CI runners.

## 1. Before you start

Status: to be verified on the VPS (issue #45).

| You need | Notes |
|---|---|
| Root SSH on the VPS | the site is at `/opt/infra/apps/raulhandyman`, `proxy-nginx` and Postgres already run |
| The site already installed | `deploy/install.sh` has run once (see the [README](../README.md#first-install-once)) |
| DNS control for `raulhandyman.net` | GoDaddy |
| A Google account for the owner | becomes the administrator |
| An S3-compatible bucket and its keys | any provider; set up in the UI, not in `.env` |
| An OpenAI API key | vision and image-edit models |
| A free local port | the admin API port is **8340** (what `deploy.sh` expects) |

Placeholders used below: `203.0.113.10` is the VPS IP, `admin@example.test` is the owner's Google account, `site-builder@example.test` is the build service user.

Never paste a key, token or real email address into a ticket, a commit or this file.

## 2. DNS

Status: to be verified on the VPS (issue #45).

1. In GoDaddy add `A  admin  ->  203.0.113.10` (use the VPS's real IP).
2. Wait for propagation, then check:

```bash
dig +short admin.raulhandyman.net
```

You should see the VPS IP.

## 3. Create the Google OAuth client

Status: to be verified on the VPS (issue #45).

1. In Google Cloud Console create an OAuth client of type Web application.
2. Authorized redirect URI: `https://admin.raulhandyman.net/api/auth/google/callback` (the platform serves `GET /auth/google/callback` under the `/api` prefix).
3. Keep the client id and secret for step 4.

## 4. Deploy the admin with `appctl deploy`

Status: to be verified on the VPS (issue #45).

The admin is deployed with the starter's CLI against the existing Postgres and `proxy-nginx`. It is **not** part of the site's Docker image (`.dockerignore` excludes `admin/`).

1. On the VPS, in a clone of this repository, build the CLI and run it from `admin/`:

```bash
cd /opt/infra/apps/raulhandyman/repo/admin
npm ci
npm run setup
npx appctl deploy --help      # install and update subcommands, and the steps they run
```

2. Provide these deployment values (the wizard writes `infra/compose/.env`):

| Variable | Value |
|---|---|
| `INITIAL_ADMIN_EMAIL` | `admin@example.test` (the owner's real Google account on the VPS) |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | from step 3 |
| `GOOGLE_CALLBACK_URL` | `https://admin.raulhandyman.net/api/auth/google/callback` |
| `APP_BIND_PORT` | `8340` |
| `SECRETS_ENCRYPTION_KEY` | generated by the wizard; back it up, losing it makes stored keys unreadable |

3. Run `npx appctl deploy install`. It brings up the stack against the existing Postgres, runs migrations and seed, and configures `proxy-nginx` for `admin.raulhandyman.net` with a certificate.

Expected result:

```bash
curl -s https://admin.raulhandyman.net/api/health | head
curl -s http://127.0.0.1:8340/api/health | head      # what deploy.sh talks to
```

Storage, AI, Web Push and SMTP are never set in `.env`: the next steps do it in the UI.

## 5. First sign-in and the Setup guide

Status: to be verified on the VPS (issue #45).

1. Open `https://admin.raulhandyman.net` and sign in with the `INITIAL_ADMIN_EMAIL` account (it bypasses the allowlist and becomes the administrator).
2. Open the administrator's **Setup guide**. Its project steps, in order:

| Step id | Opens | Done when |
|---|---|---|
| `projects.storage` | `/admin/settings/storage` | the storage config is complete |
| `projects.openai` | `/admin/settings/ai` | AI is on and an enabled model can draft copy |
| `projects.push` | `/admin/settings/push` | an active VAPID key pair exists |
| `projects.build-token` | `/admin/settings/site-publishing` | a live token of a `site_content:read` user exists |
| `projects.first-publish` | `/projects` | one project is published |
| `projects.backup` | `/admin/settings/db-backup` | the backup policy is enabled |

## 6. Storage provider and image limits

Status: to be verified on the VPS (issue #45).

1. Open `/admin/settings/storage`, choose the provider, and enter bucket, region, endpoint (if not AWS) and keys.
2. Set the upload limits:

| Setting | Value |
|---|---|
| Allowed MIME types | `image/jpeg,image/png,image/webp` |
| Max file size | 25 MB |

An empty allowlist allows every type; set it. HEIC photos are rejected by the app with a message to the editor (iPhone: Camera, Formats, Most Compatible, or share as JPEG).

3. Enable **bucket versioning** on the provider side (step 13).

Photo objects live under the key prefix `project-media/<orgId>/<projectId>/<photoId>/`.

## 7. OpenAI key and models

Status: to be verified on the VPS (issue #45).

1. Open `/admin/settings/ai`, switch AI on and save the OpenAI key (it never reaches the browser).
2. In Admin, AI, Models enable one model with image input and structured output (feature `projects_copy`) and one with image editing (feature `projects_retouch`).
3. Check Admin, AI, Usage later: usage and cost are listed per feature.

Without the first model the editor cannot get drafts; without the second, retouching is unavailable (the Doctor check `ai.projects_ready` fails or warns respectively). Retouch is never offered for `before` photos.

Status: to be verified on the VPS (issue #45).

| Setting | Where | Why |
|---|---|---|

## 9. Create the build token

Status: to be verified on the VPS (issue #45).

The platform cannot narrow a personal access token (PAT) to one permission: a PAT authenticates as its owner with the owner's permissions. So the token must belong to a dedicated service user whose only role is `site_reader` (permission `site_content:read`). If it leaks, only published content is exposed. **Never create it while signed in as the administrator or an editor.**

1. In `/admin/settings/users` add `site-builder@example.test` (use a real mailbox you control) to the allowlist and give it the role `site_reader` in the organization, and no other role.
2. Sign in once as that user (a private window; it needs a Google account for that address).
3. Create a PAT (profile, personal access tokens) with a long duration and copy it once. A PAT expires: note the date, the Doctor check `site.content_token` warns before it does.
4. Sign back in as the administrator. Check the user holds only `site_reader`.

## 10. Install the token and the cron

Status: to be verified on the VPS (issue #45).

1. Install the token into the file `deploy.sh` mounts as a BuildKit secret:

```bash
install -m 600 /dev/stdin /opt/infra/apps/raulhandyman/.content-token
# paste the token, press Enter, then Ctrl-D
ls -l /opt/infra/apps/raulhandyman/.content-token     # -rw------- root root
```

2. Re-run the site installer so it creates the cron and logrotate (it is safe to re-run; the certificate is kept):

```bash
bash /opt/infra/apps/raulhandyman/repo/deploy/install.sh
cat /etc/cron.d/raulhandyman-content
```

`install.sh` builds with the admin API URL whenever `.content-token` is non-empty (the same as `deploy.sh`), so re-running it on a site that already has published projects keeps them. With an empty token file it builds an empty portfolio, as intended.

You should see `*/2 * * * * root /opt/infra/apps/raulhandyman/deploy.sh --content >> /var/log/raulhandyman-content.log 2>&1`, and `/etc/logrotate.d/raulhandyman-content` (weekly, 4 rotations).

3. Record it in the infra notes (an instruction, not a repo file): in `/opt/infra/SERVER.md` add the admin (`admin.raulhandyman.net`, port 8340) and the cron `raulhandyman-content`, then commit in `/opt/infra`.

## 11. Verify the content pipeline

Status: to be verified on the VPS (issue #45).

1. In the admin create a project with photos and publish it.
2. Run one content rebuild by hand and watch the log:

```bash
/opt/infra/apps/raulhandyman/deploy.sh --content
tail -f /var/log/raulhandyman-content.log
```

| Output | Meaning |
|---|---|
| nothing, exit 0 | no token, admin not reachable, version unchanged, or a failed version inside its 30-minute retry window |
| `New content version <12 chars>. Rebuilding with the current code.` | a rebuild started |
| `Container is healthy.` | the new image is live and the admin was told `live` |

3. Check `https://raulhandyman.net/projects/` and the new `/projects/<slug>/`. The admin shows the build as live and the editor gets `site.build_live`.
4. `deploy.sh --content --force` rebuilds even if the version is unchanged.

How it behaves, from `deploy/deploy.sh`: a version that failed is retried at most every 30 minutes (`.content-failed` holds `<version> <epoch>`); a failed build leaves the running site untouched; a failed health check restores the previous image; the last built version is in `.content-version`; one run at a time (lock file). Production builds never use fixtures: with no token the site builds an empty portfolio, and `/projects/` is `noindex`.

## 13. Backups and bucket versioning

Status: to be verified on the VPS (issue #45).

| What | How |
|---|---|
| Database | `/admin/settings/db-backup`: enable the schedule and retention (the `projects.backup` Setup step) |
| Photos | enable **versioning** (and, if you can, a lifecycle rule for old versions) on the bucket at the provider; the app does not delete objects you did not delete |
| Portfolio export | an administrator can run the `projects` export (`projects.json` plus original and master photos, signed download that expires) |
| Secrets | back up `SECRETS_ENCRYPTION_KEY` apart from the database; without it stored keys are unreadable after a restore |

## 14. Troubleshooting

Status: to be verified on the VPS (issue #45). Open `/admin/settings/doctor` first.

| Doctor check | Symptom | Cause and fix |
|---|---|---|
| `site.content_token` fail: no token | the site never updates | no `site_reader` PAT exists: step 9, then step 10 |
| `site.content_token` fail: never used or idle over a day | token exists but unused | cron missing or the token file is empty: `cat /etc/cron.d/raulhandyman-content`; `ls -l .content-token`; step 10 |
| `site.content_token` fail: expired / warn: expires in N days | builds stop or are about to | **rotate the token**: step 9 (new PAT), overwrite the file with `install -m 600 /dev/stdin`, revoke the old PAT. The next cron tick uses it |
| `site.build_freshness` fail: last build failed | site not updated | read the error in Site publishing and `tail -n 100 /var/log/raulhandyman-content.log`; fix, then `deploy.sh --content --force`. Typical: manifest does not match `src/content/manifest.schema.json`, admin unreachable at `http://127.0.0.1:8340` (check `APP_BIND_PORT=8340` or set `ADMIN_API_URL`) |
| `site.build_freshness` fail/warn: behind by N minutes | published but not live | cron not running, a failed version waiting its 30-minute retry, or the build is slow. Force with `deploy.sh --content --force` |
| `projects.media_integrity` fail | a published photo lacks a rendition | open the project, use Reprocess on the photo; check storage is configured and the job queue (Jobs page) |
| `ai.projects_ready` fail | drafts unavailable ("AI off") | step 7: switch AI on, enable a model with image input and structured output. Warn: no image-edit model, retouch only |
| `site.indexnow` warn: no key | search engines not pinged | generate the key (Site publishing card) |
| `site.indexnow` fail | ping refused (HTTP 403/422) | the key file `/<key>.txt` is not served by the site yet (it appears after the next build) or the key changed |
| none | upload says HEIC not supported | iPhone: Camera, Formats, Most Compatible, or share as JPEG |
| none | upload refused (413 or 415) | file over 25 MB or not in the MIME allowlist: step 6 |
| none | the cron log prints `Admin API not reachable` | admin down or wrong port; `curl -s http://127.0.0.1:8340/api/health` |
| none | build log: `CONTENT_API_URL is set but no token` | the token file is empty while the admin URL is set: step 10 |
| none | the home page shows no projects after a rebuild | the build ran without a token (empty portfolio) or no project is published |

## 15. Rollback

Status: to be verified on the VPS (issue #45).

| Need | Do |
|---|---|
| Take one project off the site | in the admin, **Unpublish**; the next content rebuild (within 2 minutes) removes the page, and its old slug is kept as a redirect where applicable |
| Restore the previous site image | `deploy.sh` tags the running image `raulhandyman-web:previous` before every build and restores it automatically when the health check fails. To do it by hand: `docker tag raulhandyman-web:previous raulhandyman-web:latest && cd /opt/infra/apps/raulhandyman && docker compose up -d --no-build web` |
| Rebuild the current code and content | `/opt/infra/apps/raulhandyman/deploy.sh --force` (use after a bad `main`: revert it, push, run it) |
| Stop content rebuilds | `rm /etc/cron.d/raulhandyman-content` (re-run `install.sh` to restore); the site keeps serving its last build |
| Admin misbehaves | the public site is static and does not depend on the admin at run time; fix or redeploy the admin with `appctl deploy update`, and rebuilds resume once `http://127.0.0.1:8340` answers |
